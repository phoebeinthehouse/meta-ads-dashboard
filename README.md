# meta-ads-dashboard

Google Sheets(Apps Script Web App)를 데이터 소스로 쓰는 정적 대시보드.

| 파일 | 대시보드 | 소스 탭 |
|---|---|---|
| `index.html` | Meta Ads · Amazon US | `meta-raw-new`, `amz-raw-new`, `meta-ads-list` |
| `jp.html` | Meta Ads · Japan | `JP meta raw` |

공통 스프레드시트: **Amazon Dashboard (2025년~)**
`12IC6YbDR8s8lMEeUY69c5tejXbfnbdadbpugPkAGxT0`

## US 대시보드 (`index.html`)

광고 성과는 `meta-raw-new`(광고비·클릭·노출), 구매·매출은 `amz-raw-new`에서 읽어
소재명 기준으로 붙인다. 조인 키는 **소재명 + Creator + 제품**이다.

### By Creative 표의 ROAS

`ROAS = 해당 소재의 Amazon 매출 ÷ Meta 광고비 × 100` (%, 100% = 본전).
By Creator · By Product · Weekly 페이지와 같은 정의라 어느 화면에서 봐도 숫자가 맞는다.
광고비가 0인 행(Meta에 없고 Amazon에만 있는 소재)은 계산이 불가능해서 `—` 로 놓는다.

비율은 행끼리 더할 수 없으므로 **평균을 내지 않고** 묶을 때마다
`Σ매출 ÷ Σ광고비`로 다시 구한다 (JP 대시보드와 동일한 원칙).

### 구매·매출을 Meta 행에 나누는 방식

한 소재가 Meta에서 여러 행으로 쪼개지는 경우가 있다 — 같은 소재명이 img와 vdo로
동시에 돌거나, `캠페인 분리`를 켜서 캠페인별로 나눠 볼 때이다.
Amazon 구매는 그보다 거친 단위라 한 건을 여러 행에 그대로 붙이면 합계가 중복된다.
그래서 `allocAmz()`가 나누어 붙인다.

1. Amazon 행과 **media(img/vdo)가 같은 Meta 행**이 있으면 그쪽에만 붙인다
2. 매칭되는 행이 없거나 후보가 여럿이면 **광고비 비중**으로 나눈다
3. 구매수는 정수를 유지하되 최대잔여법으로 배분해 **합계가 원본과 정확히 같다**

Meta 행이 하나면(대부분의 경우) 예전과 똑같이 통째로 들어간다.
광고비 비중으로 나눈 행들은 ROAS가 서로 같게 나온다 — 어느 쪽이 팔았는지
원본에 정보가 없을 때는 추측하지 않고 공통 값을 보여주는 게 맞기 때문이다.

> **지금 숫자가 바뀜지는 것은 아니다.** 2026-09 US 데이터를 실제로 돌려보면
> 소재 61개 중 img/vdo가 겹치는 것도, 캐페인이 겹치는 것도 **0건**이라
> 배분 로직이 타지 않는다. UK PCO 데이터에서 1건(`ukLDhurry_Iris`)만 확인됐다.
> 즉 이건 **지금 틀린 숫자를 고치는 게 아니라, 같은 소재명을 img·vdo로 같이 돌리면
> 그때 터질 것을 막는 장치**다. 매출을 같은 경로로 붙이는 이상 필요하기도 하다.

### 정합성 확인 (브라우저 콘솔)

| 명령 | 하는 일 |
|---|---|
| `checkTotals()` | 화면 표 합계 vs 원본 시트 합계를 표로 대조. 구매·매출이 어긋나면 ⚠ 로 알려준다 |
| `checkMissingAds()` | 소재명(vdo/img 토큰)이나 제품코드를 못 뽑아 표에서 빠진 소재 목록 |

로드 직후 콘솔에 `[AMZ] 매출 컬럼: 한화매출 · 값이 채워진 행 n/m` 이 찍힌다.
매출은 반드시 **한화매출(T열, 원화)**를 쓴다 — 바로 옆 `상품판매`는 달러라
그걸 잡으면 ROAS가 1/1400로 나온다. 채워진 행이 0이면 ROAS는 전부 `—` 로 나오며,
이때는 대시보드가 아니라 시트의 한화매출 열을 확인해야 한다.

이름 규칙을 벗어난 광고(예: `vdo`/`img` 토큰이 없는 이름)는 소재를 특정할 수 없어
By Creative 표에서 빠진다. `checkTotals()`의 '원본 전체' 줄과 '인식된 행' 줄의 차이가
그만큼이니, 차이가 크면 시트의 소재명을 고쳐야 한다.

## JP 대시보드 (`jp.html`)

- 적재: strategyeric/business-report 가 매일 KST 10:00에 D-1 데이터를 `JP meta raw` 탭에 적재
- 단위: 일 × 캠페인 × 광고세트 × 광고 / 1행 헤더, 2행부터 데이터
- 원본 컬럼 A~Q (17개): YYMMDD, 일, 캠페인 이름, 광고 세트 이름, 광고 이름, 지출 금액(원화),
  노출, 링크 클릭, 조회, 동영상 3초 이상 재생, 게시물 공감/댓글/공유/저장, ShopNowClick, 보고 시작, 보고 종료
- 페이지 구성은 US 대시보드와 동일: By Creator · By Product · By Creative · Weekly Trend · Weekly Trend by Creative

### 광고 이름 규칙 (US와 순서가 다름)

```
GS_F1864_img_JP1review0902_Phoebe_260904
[0] 제품코드  [1] 타겟(파싱만 하고 사용 안 함)  [2] img|vdo
[3] 소재명    [4] Creator                      [5] 소재 live 날짜(YYMMDD)
```

`img`/`vdo` 토큰을 기준점으로 잡아 그 뒤를 소재명·Creator·live 날짜로 읽는다.
Creator와 제품 목록은 데이터에서 자동으로 뽑으므로 새 사람·새 제품이 생겨도 코드 수정이 필요 없다.

### 소재 이미지 (US `meta-ads-list` 와 같은 구조)

US 대시보드는 `meta-ads-list` 탭에서 이미지 URL을 **헤더 이름이 아니라 13번째 열(M)로 고정**해
읽는다 (`index.html`). URL 열이 여러 개인데 그중 "링크가 있는 모든 사용자"로 공개된 열만
브라우저에서 열리기 때문이다. 내부 드라이브 열을 쓰면 권한 때문에 이미지가 깨진다.

JP도 같은 구조를 따르되, 열 위치를 하드코딩하지 않고 **공개된 URL 열을 골라낸다**:

1. 헤더에 `개인` / `공개` / `personal` / `public` / `외부` 가 있는 열
2. 없으면 13번째 열(M) — US 시트와 같은 자리
3. 그것도 아니면 **마지막 URL 열** (내부 드라이브가 먼저, 공개 드라이브가 뒤에 오는 관례)

어느 열을 골랐는지는 상단 상태 표시줄과 브라우저 콘솔(`[JP IMG]`)에 찍힌다.

| 항목 | 내용 |
|---|---|
| 탭 이름 후보 | `JP meta ads list`, `JP meta ads-list`, `jp-meta-ads-list`, `JP 소재 이미지`, `JP ads list`, `meta-ads-list` |
| 이름 열 | 헤더에 `ad_name`/`소재명`/`광고 이름`/`파일명` 이 있는 열, 없으면 A열 |
| 날짜 열 | 헤더에 `일자`/`날짜`/`생성일` — 같은 이름이 여러 건이면 최신 것을 쓴다 |
| 매칭 순서 | 광고 전체 이름 완전 일치 → 부분 일치 → 소재명+Creator+미디어 → 소재명 |

드라이브 링크(`/d/<id>`)는 `lh3.googleusercontent.com` 썸네일로 변환한다.
탭이 없으면 썸네일 자리에 `no image`만 뜨고 나머지는 정상 동작한다.

### 시트에서 계산한 값 쓰기 (우선순위 1순위)

`JP meta raw` 탭의 R~U 컬럼을 시트에서 계산해 넣고 있다.

| 열 | 헤더 | 대시보드 동작 |
|---|---|---|
| R | 추정 구매수 | **읽어서 합산** |
| S | 추정 매출 | **읽어서 합산** |
| T | 추정 ROAS | 읽지 않음 — 합계끼리 다시 계산 |
| U | 추정 CVR | 읽지 않음 — 합계끼리 다시 계산 |

네 지표는 모두 화면에 나온다 — By Creator / By Product / Weekly 의 지표 탭과
By Creative 의 `전환` 탭 열로 표시된다.

**ROAS·CVR을 다시 계산하는 이유**: 한 행(하루 × 소재 하나)만 보면 시트 값과 그대로 같지만,
대시보드는 기간·Creator·제품 단위로 여러 행을 묶어 보여준다. 이때 비율을 평균 내면 틀린다
(광고비가 다른 소재들의 ROAS 평균 ≠ 전체 ROAS). 그래서 묶을 때마다
`Σ추정 매출 ÷ Σ광고비`, `Σ추정 구매수 ÷ Σ클릭` 으로 다시 구한다.

컬럼 위치는 상관없고 헤더 이름으로 찾는다 (`추정 매출(원화)`처럼 뒤에 붙어도 인식).
실제로 어느 열을 잡았는지는 브라우저 콘솔 `[JP]` 로그에 열 문자로 찍힌다.
시트에 R·S가 없을 때만 코드의 기본값(CVR 5% / 2,700엔 / 1,406.30원)으로 대신 계산한다 —
화면에 설정 입력칸은 없다.

- **추정 ROAS는 시트에 넣어도 쓰지 않는다.** 비율은 행끼리 더할 수 없어서,
  어떤 단위로 묶든 `추정 매출 합계 ÷ 광고비 합계`로 대시보드가 다시 계산한다. CVR도 마찬가지
- 컬럼이 없으면 아래 고정값으로 대시보드가 직접 계산한다 (기존 동작)

**현재 고정값** — 판매가 2,700엔 (제품 1종), 환율 1,406.30원/100엔.
`jp.html`의 `DEFAULT_SETTINGS` 한 줄이며, 구매 1건당 ₩37,970으로 환산된다.

> 고정 환율의 한계: 전 기간에 같은 배율이 걸리므로 **캠페인·소재 간 비교에는 영향이 없지만**,
> 시계열 비교와 ROAS 절대값에는 오차가 생기고 값을 바꾸면 과거 수치도 함께 바뀐다.
> 정밀도를 올릴 때는 환율보다 **프로모션에 따라 바뀌는 판매가**를 월별로 관리하는 쪽이 우선순위가 높다
> (CVR 5% 자체의 오차가 환율 변동폭보다 크기 때문).

### 판매가 · 환율 탭

추정 매출은 달마다 다른 판매가(프로모션)와 월평균 환율을 반영한다.
`jp.html`의 `PRICE_SHEETS` / `FX_SHEETS` 후보 이름으로 시트 탭을 찾아 읽는다.

- 환율은 **100엔 기준**으로 입력·저장한다. 시트 값이 100 미만이면 원/엔으로 보고 100배 환산한다
- 인식 형식: **한 행에 「월 + 숫자」** (예: `2026-01 | 1406.30`). `YYYY-MM`, `YYYY.M`,
  `2026년 1월`, `YYYYMMDD`, 날짜 셀 모두 월로 인식하고, 그 뒤 첫 숫자를 값으로 쓴다
- 안전장치: 탭 상단 4행에 `환율/엔화` · `판매가/가격` 키워드가 없으면 무시한다
  (엉뚱한 탭을 읽어 잘못된 ROAS를 내지 않도록)
- 탭을 못 찾으면 위 고정값으로 계산한다. 판매가나 환율을 알 수 없는 기간이 생기면
  추정 매출·ROAS를 0이 아닌 `—` 로 표시하고 안내 문구를 띄운다

데이터는 브라우저 localStorage에 30분 캐시된다. 상단 `↻ Refresh`로 캐시를 지우고 다시 불러온다.

> `jp.html`은 Apps Script Web App이 `?sheet=JP meta raw` 요청을 처리한다는 전제로 동작한다.
> 스크립트에 시트 화이트리스트가 있다면 `JP meta raw`를 추가해야 한다.
